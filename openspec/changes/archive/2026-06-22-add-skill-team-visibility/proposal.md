# Skill集成团队功能 - 提案

## 1. 需求背景

### 1.1 业务需求
当前系统中Skill的可见性仅支持 PUBLIC（公共）和 PRIVATE（私人）两种模式：
- PUBLIC: 对全平台所有用户可见
- PRIVATE: 仅创建者可见

但实际业务场景中，存在**团队协作**需求：某个团队创建的技能需要对团队内所有成员可见，而非仅对创建者个人可见，同时又不希望对整个平台公开。

### 1.2 需求描述
根据业务/产品描述：
（1）本次调研围绕「Skill集成团队功能」核心需求，只在skill-gateway项目中添加新功能
（2）调整SkillController类中已存在的添加和编辑Skill功能，在Skill对象的SkillVisibility字段中添加"团队"选项
（3）数据库中Skill表中添加team_id字段，如果用户选择"团队"选项，记录UserTeam类中的id字段
（4）不使用数据库外键

### 1.3 预期效果
- 用户创建Skill时可选择"团队"可见性
- 选择"团队"后需指定关联的团队ID
- 团队成员可查看该Skill
- 团队创建者或Skill创建者可修改该Skill

## 2. 价值分析

### 2.1 业务价值
- **团队协作支持**：团队成员可以共享和协作使用团队级技能
- **权限精细化**：介于个人私有和全平台公开之间的中间权限层级
- **数据隔离**：团队技能仅对团队成员可见，保护团队内部资产

### 2.2 技术价值
- **扩展性**：为后续团队级功能奠定基础
- **向后兼容**：不影响现有PUBLIC/PRIVATE技能的行为
- **非侵入式**：不修改数据库外键约束，通过业务逻辑保证一致性

## 3. 范围界定

### 3.1 包含范围
- 在 SkillVisibility 枚举中添加 TEAM 选项
- 在 Skill 实体中添加 	eamId 字段
- 修改 SkillService 的权限判断逻辑
- 修改 SkillMapper 的查询逻辑
- 更新数据库表结构添加 	eam_id 字段

### 3.2 排除范围
- 不修改 agent-core 项目
- 不添加新的 REST API 端点（复用现有CRUD接口）
- 不创建数据库外键约束

## 4. 风险评估

| 风险 | 等级 | 描述 | 缓解策略 |
|------|------|------|---------|
| 数据一致性 | 中 | team_id 可能指向不存在的团队 | 在业务层校验团队存在性 |
| 查询性能 | 低 | 团队成员查询可能影响性能 | 添加 team_id 索引 |
| 权限泄漏 | 中 | 非团队成员可能访问团队技能 | 严格的权限校验逻辑 |
| 团队删除 | 低 | 团队删除后关联技能状态 | 删除团队时清理关联技能 |
